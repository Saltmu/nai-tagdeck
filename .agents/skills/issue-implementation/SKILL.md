# Issue の実装

## 着手から PR 作成まで

1. 対象リポジトリの GitHub Issue を開き、依頼内容と完了条件を確認する。番号や URL がなく既存 Issue を特定できない場合は、対象 Issue または Issue 作成の指示をユーザーに求める。対象 Issue を確認できるまでコードを変更しない。
2. `git fetch` でベースブランチのリモート参照を更新し、その参照からワークスペース内に Issue 専用の worktree とブランチを作る。たとえばベースが `main` なら `git worktree add -b issue/123 worktrees.local/issue-123 origin/main`。同じ Issue の作業を再開する場合は既存の worktree とブランチを確認して使う。以降の編集と検証はその worktree 内で行う。
3. `AGENTS.md` に沿って実装と動作確認を行う。確認に使ったコマンドや操作、結果、未確認項目を記録する。
4. コミットを push し、下記のテンプレートに沿って Issue を参照する PR を作成する。PR がすでにある場合は更新する。PR コメントに実装時の確認内容と結果を記載する。

## Issue と PR のテンプレート

- 新規 Issue の作成を依頼された場合は、不具合なら `.github/ISSUE_TEMPLATE/bug_report.md`、機能追加・改善や技術的な変更なら `.github/ISSUE_TEMPLATE/change_request.md` を使う。既存 Issue では、対応範囲や完了条件を読み取り、実装の判断に必要な情報が足りなければ確認する。
- PR 本文は `.github/pull_request_template.md` に従う。既定ブランチへのマージで Issue が完了する場合は本文に `Closes #123` を使う。継続する場合や既定ブランチ以外を対象にする場合は `#123` で参照する。
- `gh` と GitHub MCP のどちらで作成する場合も、テンプレートの見出しに実際の内容を記入した本文を明示的に渡す。Issue テンプレートの YAML フロントマターと記入ガイドの HTML コメントは投稿する本文から外す。

## Codex CLI レビューと対応

1. PR コメントから開始済みのターン番号を確認する。PR のベースを取得し、worktree に未コミットの変更がなく、HEAD と取得したベースのコミットがそれぞれ GitHub 上の PR の head と base に一致することを確認する。`git merge-base HEAD <ベースの SHA>` でマージベースを求める。
2. レビュー 1 回とその指摘への対応を 1 ターンと数える。`codex review --base <ベースの SHA>` を実行する前に、ターン番号、head とマージベースの SHA を PR コメントに投稿する。投稿を確認できた時点でそのターンを開始済みとし、中断したターンも上限に含める。
3. レビューが終わったら、同じターン番号で確認内容、結果、指摘を PR コメントに記録する。指摘ごとの対応または見送った理由も記録する。修正した場合は関連する確認を再実行して push し、確認結果と修正後のコミットを記載する。指摘がなかった場合も結果を記録する。Codex CLI を実行できない場合やレビューが失敗した場合は、その状況を記録し、レビューの完了とは扱わない。
4. 対応が必要な指摘が解消し、最新の PR の head とマージベースがレビュー済みの組と一致した時点で完了とする。修正やベース変更でこの組が変わった場合は、次のターンで再レビューする。中断後に再開する場合、記録済みのレビュー結果があればそのターンの残りの対応を続ける。レビューを再実行する場合は次のターンとして扱う。
5. 自動で進めるのは最大 5 ターン。5 ターン目の修正の再レビューを含め、次のターンが必要なら、未解決の指摘や再確認が必要な箇所を PR コメントに残し、PR の URL を添えてユーザーに判断を求める。人間の確認があるまで 6 ターン目は開始しない。

## GitHub 操作

- Issue の確認、PR の作成・更新、PR コメントの投稿は `gh` を優先する。実行前にグローバルの Codex ネットワーク設定で必要な GitHub ドメインを許可する。対象の操作に `gh` を使えない場合は GitHub MCP を使う。
- 複数行の Issue・PR 本文やコメントを `gh` に渡す場合は、worktree 内の Git 管理外にファイルを置き、`--body-file` を使う。着手前に Issue を作成する場合は、ワークスペース内の Git 管理外に置く。
